# Conversation recovery consistency

Core job -> recover deleted history from either entry -> preserve an accurate
conversation list and an executable Undo action -> notify changes by backup ID.
Restore/delete/expire -> update only successful records -> refresh derived state
-> retain payloads and Undo when an operation fails.

Existing invariants -> compact native dialogs and shared controls -> deletion
consequence, current conversation, command -> reuse Notice and existing dialogs
-> no new page CSS or broad component migration.

| Owner | Surfaces | States | Evidence |
| --- | --- | --- | --- |
| Recovery events and list cache | Settings, Conversations | mounted/unmounted, restored/deleted/failed/unrelated | renderer and Electron |
| Recovery controller focus key | Settings, Conversations dialogs | list/preview/confirm/loading/busy | keyboard and Electron |
| Backup presentation | list, filter, Settings storage | locales, mixed object counts | renderer and captures |
| Warning primitive | deletion confirmation | minimum/normal window, en/zh_CN | current desktop captures |

Reject the reported direct-row restore defect: the current Restore button is
available only in preview. Preserve the existing return-to-list behavior and
cover it from both entries. The deletion dialog already uses shared ModalFrame
and DialogHeader/Body/Footer. Improve warning emphasis without rebuilding it.

Undo remains available after unrelated refreshes, unrelated backup changes and
failed deletion. Expiration notifications enumerate successfully deleted records;
failed cleanup records do not invalidate their Undo. Restoration invalidates the
module-owned list cache even when Conversations is unmounted. The two dialog
entries derive focus from the same controller state and account for loading/busy
controls becoming available.

Focused verification: 83 domain/renderer tests passed. Current macOS Electron
tests passed in English and Simplified Chinese, covering both entry points,
occupied-destination refusal, restoration, prefetch invalidation and removal of
Undo after permanent deletion. Subview focus is checked in the real desktop
process. Deletion at 920/1180/1440 and recovery at 920/1440 were captured; minimum
English/Chinese deletion and recovery/error pixels were inspected. No page CSS
was added. The two changed warning baselines were updated after inspection.

The full completion receipt is `docs/verification-snapshot.json`, generated by
`npm run verify:product` from the rebuilt artifact, tests, audits and captures.
The deletion E2E now belongs to the serialized Electron group, and its registered
captures are produced by full product verification as well as visual verification.
Packaged and other-platform execution are separate from this local desktop check.
